Explicit offline core roles

These scripts target a new isolated PostgreSQL 18 database. They do not initialize schema, upgrade data, change production or run during startup/package installation. Keep the administrator, NOLOGIN object owner and restricted runtime separate. Go extensions never receive a core credential.

Run create-core-roles.sql explicitly as database administrator before explicit lmm-core --config /absolute/private-init.toml init-db. It creates NOLOGIN lmm_core_owner and unprivileged LOGIN lmm_core_runtime without a password. Existing same-name roles reject the transaction; this is not a repair/reset tool. PUBLIC loses database CREATE/TEMP and public-schema CREATE; only the offline owner receives installation CREATE.

Set the runtime password in an interactive private administrative psql session:

text
\password lmm_core_runtime

For Docker, use the complete dc function from the Docker guide:

sh
dc exec core-db psql -X -U lmm_core_admin -d lmm_core

Use the same secret in the runtime URL file. Never put passwords in psql -c, -v, Docker arguments, shell history or evidence. The isolated fixture uses synthetic passwords and sends administrative SQL over private stdin.

The install URL authenticates the administrator and includes connection option options=-c%20role%3Dlmm_core_owner. Session user remains administrator while current user and new application objects belong to the NOLOGIN owner. Runtime gets no owner membership. Verify actual object ownership after installation; do not use whole-cluster REASSIGN OWNED. Mount this URL only into core-init.

Select an absolute version 1 init TOML whose [database] url_file references only the private owner URL file. Do not select the runtime TOML or use legacy environment configuration. The Docker core-init service already selects its separate init template and owner secret.

Run that explicit --config init command once, then execute grant-core-runtime.sql as administrator. Its non-secret, quoted psql identifier variable runtime_role defaults to lmm_core_runtime. Feature switches default to false:

psql variable Explicit capability
No feature flag Identity, read-only ledger, controlled ledger functions
enable_events=true RPC events and durable inbox/outbox
enable_console=true Read-only config/setup and append-only announcement reads
enable_models=true Charging and controlled model checkpoint/recovery functions
enable_web_identity=true Budget management and read-only consumption for legacy Web identity
enable_federated_auth=true Federated provider configuration, bindings and one-time authentication flows with column-limited writes
enable_commerce=true Commerce, charging, events and original-order partial refunds through the closed money function
enable_community=true Read-only community aggregates (rankings, profile cards, onboarding facts)
enable_payments=true Payment intents/refund holds and append-only receipts/proofs
enable_assistant=true Personal assistant and charging, including read dependencies of agent charge guards
enable_assistant_tools=true Business-facts reads and browser confirmation state
enable_assistant_agent=true Assistant and charging plus column-limited durable agent journals

These flags grant rights only: they do not enable HTTP modules or supply provider credentials. There are no wildcard grants or default ACLs for future objects. Legacy Web identity alone cannot write model requests, holds or consumption. Import records remain read-only. Runtime receives no opening-balance import function, owner switching, DDL, TRIGGER, direct ledger or model checkpoint writes. The grant script is additive by default. When a capability is disabled, an earlier run can still leave its runtime ACLs in place. Revoke those optional ACLs in a reviewed offline session, then re-apply the final flag set in one maintenance window:

sh
# Run as the private database administrator, while the runtime is stopped or
# otherwise fenced from requests. The explicit confirmation is required.
dc exec -T core-db psql -X -U lmm_core_admin -d lmm_core \
  -v ON_ERROR_STOP=1 -v runtime_role=lmm_core_runtime \
  -v confirm_revoke=true < deployment/postgres/revoke-core-runtime.sql

# Include every capability that should remain enabled; this is only an example.
dc exec -T core-db psql -X -U lmm_core_admin -d lmm_core \
  -v ON_ERROR_STOP=1 -v runtime_role=lmm_core_runtime \
  -v enable_models=true < deployment/postgres/grant-core-runtime.sql

revoke-core-runtime.sql resets only optional capability schemas and the optional Web routing, assistant and CREDIT-v2 tables. It preserves the baseline identity, ledger, history, abuse, gift qualification and billing authority. It never runs during startup and does not change ownership, passwords or default ACLs. Re-run grant-tool-market-credit.sql with the same explicit -v runtime_role=lmm_core_runtime after the reset when that separate installer-only complement is required.

Check-in rewards on component 75 additionally use grant-checkin-challenges-runtime.sql, with an explicit -v runtime_role=lmm_core_runtime, after installing or upgrading the schema and applying native Web identity/account-security grants. The separate script grants only challenge reads/inserts/expired deletes, the three state columns, and append-only reward receipts. It does not enable the removed legacy Core check-in HTTP route. Its ACLs are not reset by the historical revoke-core-runtime.sql; revoke them explicitly when disabling this capability.

Startup independently checks exact authority and enabled capabilities before binding a listener. Roles/GRANTs are excluded from the catalog fingerprint and do not change schema definitions. Actual container acceptance remains separate from static SQL/Compose checks; run the new fixture on final frozen sources before claiming the Docker flow works.
