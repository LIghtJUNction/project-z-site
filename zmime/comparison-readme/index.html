Reproducible comparison with mail-parser

This independent workspace compares zmime with mail-parser 1.0.1, pinned in Cargo.toml with transitive versions fixed by Cargo.lock. It does not enter the published crate's dependency graph or package. The comparison needs Rust 1.98 or newer because that is the reference library's minimum version; zmime itself has an independently tested Rust 1.74 minimum.

The experiment covers borrowed RFC 5322 headers, MIME structure, and transfer decoding. It makes no full-parser or complete character-set performance claim. Both parsers receive exactly the same generated bytes. Every timed mail fixture first passes an equality check of its part tree, header names and raw values, Content-Type and Content-Disposition parameters, transfer encodings, and raw body bytes. The benchmark stops before timing if those checks fail. The timed consumers also read every supported MIME metadata field and decode every quoted parameter value into reusable scratch space. This includes work that zmime normally defers and mail-parser performs during parsing. Matching consumer checksums are asserted before timing, in addition to the full byte and tree projections; attachment transfer decoding remains separate.

Reproduce#

From the repository root, with cargo, rustc, and Python 3.9+ on PATH:

sh
cargo test --locked --manifest-path comparison/Cargo.toml
python3 comparison/run.py --output comparison/results/local --samples 9 --target-ms 20
python3 comparison/run.py --portable --output comparison/results/local-portable --samples 9 --target-ms 20
python3 comparison/report.py comparison/results/local comparison/results/local-portable > comparison/RESULTS.md

The runner builds both libraries with the same release profile: thin LTO, one codegen unit, and the compiler's default target CPU. On Linux it pins the timed process to one available CPU; --cpu N selects another allowed CPU. On platforms without affinity support, it records that limitation. It records compiler versions, CPU capabilities, source revision, tracked modifications, feature selection, sampling settings, and timing scope in environment.json. The record also includes SHA-256 hashes of implementation and experiment source, benchmark executables, and every generated mail fixture. Collection fails if source or executables change during the run. compare --dump-corpus DIRECTORY validates the corpus and writes its exact .eml files without running timers.

Each output directory contains every sample in raw.csv and median, minimum, and maximum timings in summary.csv. The reported ratio is mail_parser_ns / zmime_ns: values above one favor zmime, values below one favor mail-parser. Results with different storage lifecycles have an empty ratio. There is no aggregate score across different modes or input sizes.

cold.csv separately measures the first flat-Base64 decode in a fresh process and a subsequent warmed loop for each library. Process creation and buffer preparation are outside those timings. No cold speed ratio is calculated: CPU feature detection, instruction-cache state, and each API's initialization are being observed separately. On x86_64, zmime caches its detected SIMD backend in a private atomic; its first decoding call may be noticeably slower on a virtualized CPU. Both libraries' dispatch caches are warmed in the main results.

For a shorter targeted run:

sh
cargo run --release --locked --manifest-path comparison/Cargo.toml --bin compare -- \
  --filter structure_reuse --samples 9 --target-ms 20 > structure.csv
python3 comparison/summarize.py structure.csv

Work performed in each mode#

The reference configuration keeps non-MIME headers in HeaderForm::Raw, matching the raw-header API evaluated here. It still parses Content-Type, Content-Disposition, and Content-Transfer-Encoding. Address lists, dates, Received semantics, RFC 2047 text, and character-set conversion are outside these parse timings. Both libraries preserve those header bytes. Separate differential tests cover the supported RFC 2047 character sets.

Mode zmime operation Reference operation Timed output and storage
headers Part::parse_headers MessageParser::parse_headers Validate and parse root headers and MIME metadata; consume every raw header and decoded parameter value; body remains opaque. The reference's public headers API allocates its result storage.
structure_reuse Message::parse with reusable part storage parse_with with reusable MessageBuffers Complete supported MIME tree and metadata; consume all raw header/body views and decoded parameter values; no attachment decoding. Both receive warmed storage.
structure_fresh_reference Message::parse with reusable storage parse with new storage Additional API-lifecycle observation. Storage lifecycles differ; no speed ratio is calculated.
transfer_base64 decode_base64 into a caller slice Encoding::Base64.decode_append into a cleared, reserved Vec Decode every encoded byte to the same bytes; output storage is reused. Flat and MIME-wrapped inputs are separate.
transfer_qp decode_quoted_printable into a caller slice Encoding::QuotedPrintable.decode_append into a cleared, reserved Vec Decode every byte; plain ASCII and escaped inputs are separate; output storage is reused.

The reference builds its body-role indexes as part of parsing. zmime builds its borrowed part records. These internal representation costs remain in the measurements. Construction of the reference parser configuration, fixture generation, workspace creation, output reservation, and equality checks occur outside timed regions. Transfer output is passed to black_box; parse timings also consume header and body views so the compiler cannot discard the results. MIME parameter scratch is reserved outside timing, while parameter traversal and unescaping are timed. Header values are compared and consumed without their final physical line ending because the APIs expose that delimiter differently.

Both libraries use lazy transfer decoding. In particular, parsing the large attachment fixture does not decode its Base64 body in either implementation. Using an earlier eager version of mail-parser would measure a different workload; this experiment uses the current 1.0.1 API for that reason.

Inputs and correctness coverage#

The corpus is generated by src/corpus.rs; it contains no personal mail and requires no network downloads. Each mail category has CRLF and LF variants:

Category Contents
Tiny One header and a one-byte body
Ordinary Common RFC 5322 fields, a folded custom field, UTF-8 text
Large attachment One MiB of deterministic bytes encoded as wrapped Base64, plus a text part
Nested multipart Eight nested multipart containers with sibling parts
Newsletter Plain-text and HTML alternatives carried in a multipart container, with quoted-printable content
Long headers A logical header with 100 folded lines and approximately 70 KiB of field data
Many attachments 128 Base64 attachments with type, disposition, and filename parameters
Nested message An unencoded message/rfc822 attachment inside a multipart

Additional tests compare 300 generated multipart messages, 96 generated nested trees with quoted-pair filenames and folded metadata, independently encoded arbitrary-byte transfer round trips, supported UTF-8/US-ASCII/Latin-1 encoded words, and 7,200 deterministic random or mutated inputs. These tests supplement the core crate's RFC examples, resource-limit, alignment, buffer, and Miri tests. Generated fixtures exercise controlled features; they do not substitute for long-term validation on a diverse production mail corpus.

Malformed and truncated inputs have explicit policy tests and no speed ratios. zmime returns structural errors and rejects malformed transfer encodings on access. mail-parser attempts recovery. For example, mail-parser 1.0.1 accepts unpadded SGVsbG8 and terminal quoted-printable abc= without a problem flag; the strict zmime decoders reject those inputs. Invalid Base64 alphabet and invalid quoted-printable hex are also exercised. Comparing rejection with recovery would measure different tasks.

Character-set equivalence is also limited to shared behavior. zmime implements literal ISO-8859-1, while mail-parser maps that label to Windows-1252: an encoded word carrying byte 0x80 produces U+0080 in zmime and € in the reference. A policy regression records that difference. Character-set conversion is absent from parse and transfer timers, and the encoded-word equality cases do not claim equivalence for the differing 0x80–0x9F mapping. The reference behavior is documented on its Charset::Windows1252 variant.

Sampling and the SIMD ablation#

Each pair has 32 warm-up iterations followed by a calibration pass. The same iteration count is used for both libraries, and sample order alternates to reduce order bias. The default records nine paired samples and targets at least 20 ms per sample for the faster library. There is no outlier deletion. The minimum and maximum accompany the median so scheduler variation is visible.

--portable disables zmime's SIMD feature while retaining the identical fixtures, compiler profile, reference library, and output checks. Comparing default and portable rows measures the contribution of zmime's scanning and transfer-decoding kernels. The reference continues to select its own available kernels. This ablation does not imply equal instruction sets, and measurements on one CPU do not establish throughput on aarch64, WASM, or another x86_64 processor.

Evidence and limits#

Claim Evidence Scope
Timed mail results agree Equality checks run before the first timing Header bytes, metadata, tree, raw bodies in the generated supported subset
Attachments remain lazy Parse modes access raw bodies only; transfer modes are separate Both evaluated APIs
A measured scenario is faster or slower Median paired samples plus full raw CSV Recorded machine, toolchain, fixture, feature selection
SIMD contributes to a result Default/portable runs with unchanged inputs The kernels enabled by zmime's feature
Unsupported features are explicit Core API errors and differential policy tests No claim of all mail-parser charsets or all recovery policies

The review questions are concrete: does the comparison preserve the same observable result, use a recent fixed baseline, disclose storage lifecycles, retain slow cases, and limit conclusions to measured inputs and hardware? The protocol above addresses each question. No result from this workspace supports a claim that zmime defeats mail-parser's full feature set.

The reviewed measurement protocol reads decoded parameter values inside timing. Older 2026-11-10-default and 2026-11-10-portable results retained in this repository used shallower timed consumers. Their pre-timing equality checks were valid, but those rows do not establish the cost of materializing all MIME metadata and are not used for current speed claims. Current results use the reviewed- directories linked from RESULTS.md.

Reference APIs and source: mail-parser 1.0.1, upstream repository.
