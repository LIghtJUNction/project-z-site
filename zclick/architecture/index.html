Architecture and dependency boundaries

zclick separates token processing from Python's object protocol. The fixed behavioral reference is Click 8.5.1. A Python callback is an arbitrary program: it may mutate an option, replace a converter, invoke another command, or raise an exception. Keeping these operations observable is part of the interface, rather than an optional slow path.

What runs where#

Component Responsibility Runtime dependencies
python/zclick Public classes and decorators, context lifecycle, overridable parameter hooks, defaults and environment lookup, type conversion, help assembly, terminal utilities, completion and testing Python standard library
crates/zclick-python PyO3 binding, parser action orchestration, command group dispatch, Python object ownership PyO3 and the local Rust core; std
crates/zclick-core Argument consumption, option recognition adapter, positional allocation, eager ordering, value-source arbitration, ANSI and text wrapping Exactly registry zclap = "=0.1.4"; no_std + alloc
zclap Actual recognition of normalized option tokens through its event parser Its published dependency graph

This is a hybrid implementation with substantial Python responsibilities. Python owns the public object model and dynamic hooks listed above; Rust owns token and arity processing, parameter ordering, source arbitration, group dispatch and the text primitives used by the Python help formatter. The boundary preserves ordinary subclass overrides and Python object semantics.

The core obtains successful option matches from zclap's Event::Flag and requires the parser's final finish() check. Schemas store full hashes to choose small candidate tables; the hash does not establish a match. Each candidate must still be accepted by zclap, including an explicit regression which forces a full hash collision between different spellings. Each candidate command contains one argument and uses zclap's parse_with::<1, _> presence storage. This reduces initialization for each recognition attempt; the enclosing schema may still contain any number of parameters, and both event exhaustion and final validation remain required. Consumed values also pass through zclap's byte-input parser, with a terminator that preserves Click's treatment of dash-leading values. These paths are implemented in parse.rs. The Rust semantic layer supplies the Click rules that differ from zclap's default value consumption, help and parent-command conventions, as recorded in COMPATIBILITY.md.

The Python extension is not a no_std program. It allocates Python objects, uses PyO3 and its required build/transitive dependencies, and links to the interpreter. Python runtime requirements are empty. Maturin, pytest, Hypothesis, mypy and original Click belong to build or comparison environments. audit_dependencies.py verifies these boundaries; check_wheel.py inspects the actual distribution, including its namespace and dependency metadata.

One invocation#

The public command asks its current parameter objects to register with a fresh parser. The binding validates or replaces the parser's owned, immutable Rust schema, while execution state remains local to the call. The schema owns names which zclap borrows during parsing. No argument name is leaked or permanently interned, and no borrowed value is given a fabricated 'static lifetime.

The binding reuses a finite set of source-code protocol names, such as nargs and process, through PyO3's intern! facility. These fixed names do not contain command names, option aliases, input values or application objects. Every attribute lookup and method call still executes against the current Python object. The main-interpreter restriction below applies before these Python string caches are initialized.

The Python parser uses one native entry point for validation and execution. It publishes the new plan before constructing the current Python parsing-state object or evaluating flags, so a constructor or getter can reenter the parser. Factories and sentinels are read from the interpreter's live module namespace; temporary factories and context values are released at their original Python evaluation boundaries. The low-level plan methods remain available for direct use and for the separate-path comparison tests in test_native_parse_live.py.

The Rust core recognizes tokens, consumes values using Click's rules, allocates positional arguments and records encounter order. The binding invokes the current Python parser action for each event, including overridden actions. Parameter scheduling preserves Python's stable sorting, first matching invocation index and eager-option behavior. On CPython, exact lists with at least 512 declared parameters may use guarded native ordering for ordinary object protocols. Smaller lists, custom comparison or attribute protocols, and PyPy use the live Python sorted and index operations. The implementation and regressions are in ordering.rs and test_native_ordering.py.

Rust supplies value-source arbitration. Python parameter hooks perform the requested conversion and callback with the current context. Environment lookups, callable defaults and prompting happen for that invocation.

Group invocation is driven by Rust. It resolves child commands through virtual Python methods, calls custom make_context and invoke methods, handles chained commands, and invokes result callbacks while the appropriate resources remain open. A small Python with helper preserves the interpreter's handled-exception state. Consequently a user-defined __exit__ sees the real exception and traceback, and exception suppression has the same meaning as a Python context manager. The library never terminates the process through Rust std::process::exit.

Mutation, recursion and ownership#

Each command or parser retains at most its most recent immutable native schema. Before reuse, the binding reads the current option aliases, arity, flag behavior and optional-value behavior. A difference builds a new owned schema; matching definitions reuse the existing schema without reconstructing every string and lookup table. The schema contains Rust data only. It holds no Python command, context, callback, default result or environment value. Its pickle protocol serializes only those structural fields, so a warmed command remains copyable and pickleable whenever its ordinary Python fields permit that operation.

Definition validation walks exact Python lists with a live cursor, checking their current length at each step. A getter that inserts or removes a later definition therefore affects the same traversal. List subclasses retain their Python iterator protocol. This saves an iterator allocation without taking a fixed-length snapshot; the regression cases cover append, deletion, insertion and custom iteration.

make_parser, parameter registration hooks, parser actions, conversions and callbacks still run through their current Python methods. Replacing a callback, modifying an option, changing a type method or registering a command is visible to the next invocation. Callable defaults, environment lookups and prompts are evaluated for each invocation. The benchmark includes definition validation and all Python binding and object-construction costs.

Callbacks may reenter the same command. No native lock or mutable PyO3 borrow is held across a call to user Python code. Parsing state is local to one call.

Native dispatch frames expose their captured Python references to garbage collection through explicit traversal. They also release those references when the complete Python context scope returns or raises. This deterministic cleanup breaks retained extension-callback cycles on PyPy while keeping the callback usable throughout the active scope, including __exit__ and resource cleanup. The mutable PyO3 borrow ends before captured references are released, so a Python finalizer can reenter safely. These rules are implemented in dispatch.rs.

The ordering guard uses a small explicit CPython FFI boundary in addition to the interpreter check described below. PyType_GetSlot reads documented Stable ABI slots whose addresses are compared to classify object protocols; the code does not invoke those addresses. PyObject_GenericGetDict obtains the ordinary instance dictionary without running a user-defined __dict__ descriptor. Its new reference is immediately wrapped in a PyO3 owned handle, which handles the error case and eventual release. These calls use documented APIs without reading private interpreter layouts or writing reference-count operations.

Ordinary UTF-8 strings borrow the live PyString buffer for the duration of the native call. The binding retains the Python owners throughout parsing and records argument indices explicitly, rather than using buffer addresses as object identities. Distinct empty string subclasses therefore remain distinct. Python strings containing surrogate code points use a reversible surrogatepass representation at the boundary. Values originating as whole argument objects retain their Python identity where the reference parser does. There is no lossy UTF-8 conversion. Integer conversion uses Python integers and therefore does not introduce an i64 or u64 limit. Open files and user-provided streams preserve Python ownership and closing behavior.

These properties have focused regressions in test_dynamic_semantics.py, test_native_dispatch.py and test_native_kernel.py. The larger official suite checks the behavior exposed by the fixed Click version.

Interpreters and concurrency#

The standard CPython wheel uses the stable ABI with a Python 3.10 minimum. Free-threaded CPython and PyPy builds disable that ABI feature and build for their interpreter.

The CPython extension currently supports the main interpreter only. zclick's mutable parsing state and dispatch handles are local to an invocation, but the pinned PyO3 0.30.1 binding has process-global Python-object caches, including the iterator length-hint callable used in stable-ABI builds and native type state. These caches are not partitioned by interpreter. Subinterpreter support therefore remains an unfinished compatibility item, including subinterpreters that share the main interpreter's GIL.

The first operation in zclick's standard PyO3 module initializer checks PyInterpreterState_GetID(PyInterpreterState_Get()) == 0 and raises ImportError for other IDs. Both identity queries are part of CPython's stable C API; the supported CPython 3.10–3.15 sources assign ID zero exclusively to the main interpreter (see pystate.c). CPython invokes module initialization with the current thread attached, so the queries receive a valid current interpreter. They do not create Python object references or require manual reference counting or interpreter-structure access. The implementation retains PyO3's standard module initialization and does not declare subinterpreter support.

The package imports the native module before its Python public modules, so an unsupported import is rejected before those modules initialize additional native state. The CPython identity check is excluded from PyPy builds, which do not provide CPython's subinterpreter API. The guard and its import-order regressions are in interpreter.rs and test_interpreter_isolation.py. The tests cover default and legacy shared-GIL subinterpreters, both import orders, continued main-interpreter operation after rejection, and prevention of calls to a main-interpreter cached callable from a child interpreter.

Tiny parser calls keep their interpreter attachment; releasing and reacquiring it for every token would itself add overhead. No GIL speedup is claimed without a workload-specific measurement.

CliRunner intentionally changes interpreter-wide streams, environment values and, for filesystem isolation, the process working directory. Its isolation operations are not thread-safe. Use separate processes for parallel runner tests. Per-call native parser state does not change that public testing-tool boundary.

Toolchain and licensing#

The checked-in toolchain and declared MSRV are Rust 1.99.1, Edition 2024. This is the version used for compilation and CI, not a lower version inferred from one dependency's metadata. The registry version and checksum are fixed in Cargo manifests and Cargo.lock; release builds use --locked.

Runtime implementations are written for this project. Public type declarations are generated from the fixed Click API and retain Click's BSD attribution in CLICK_LICENSE.txt, included alongside the project's MIT license in distributions. Upstream behavioral tests remain comparison inputs outside the runtime package.
