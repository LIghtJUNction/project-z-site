Measured performance: 0.1.1a2

Two independently recorded Linux hosts show a large improvement over published zclick 0.1.1a1 in reused parsing: the 1,000-option median ratios are 2.535× locally and 2.354× in release CI. Complete warm invocation at that size measured 1.771× and 2.017× relative to Click 8.5.1. Its improvement over a1 is much smaller: 1.042× locally and 1.050× in CI.

The parser comparison with Click differs between hosts. The local 1,000-option ratio of 1.236× was not reproduced in CI, which measured 0.975×. Parsing with 1, 10 and 100 options, the one-option warm invocation and the nested-command case remained slower than Click on both hosts. Unicode/ANSI wrapping measured 7.404× locally and 9.314× in CI relative to Click. These are workload comparisons, not a universal application speedup.

The local schema-2 report and release-CI schema-2 report preserve all samples and distribution identities. Their results are presented separately below; neither replaces the other. The published a1 wheel was measured again alongside the candidate in each run. The 0.1.1a1 report retains its original historical measurements.

Local source, distributions and environment#

  • Measured source: c949d301f815c882acce9a96fe2a0c3b8da9bded, version 0.1.1a2. The working tree was clean before and after measurement.
  • Reference: Click 8.5.1 at the fixed target; published baseline: zclick 0.1.1a1 from commit 3281e18f215dec976c3ce0c4b5dd933ad4d62616.
  • Time: 2026-11-11, 15:41:54–15:42:47 UTC; approximately 53.31 seconds for the complete run.
  • Interpreter: CPython 3.12.14, built with Clang 22.1.3; ordinary GIL build.
  • Host: Linux 6.18.57 x86-64, glibc 2.41, AMD EPYC 9V74 80-Core Processor. Nine logical CPUs were available to the process; the orchestrator and every recorded warm worker used CPU affinity [0].
  • Method: twelve rounds, two complete blocks of all six implementation orders, seed 20261111, five warmup calls per case and normal garbage collection enabled.
  • Build dependencies: Rust 1.99.1 / Edition 2024, registry zclap 0.1.4 and PyO3 0.30.1. The raw report retains Cargo.lock and native-file hashes.

The published baseline is a manylinux_2_17 wheel; the candidate was built on this host as manylinux_2_34. Python, measurement host and execution ordering were controlled, while the wheel build environments were not identical. This is a comparison of these distributions; their entire difference cannot be attributed to source changes alone. The separate release-CI section below uses the distribution build environment and keeps this local result intact.

The parser improvement grows with command size. Its median ratio against a1 ranges from 1.231× at one option to 2.535× at 1,000 options. At 100 options, the 2.370× version improvement still leaves a2 behind Click: 64.755 µs versus 56.213 µs. Reusing an owned schema removes repeated setup, while validation, Python object creation and the current parser actions remain part of the call. The measurement does not assign a separate time to each of those costs.

Complete invocation includes more than parsing. With 1,000 options, a2 took 5.642 ms, compared with 9.990 ms for Click and 5.878 ms for a1. Context creation, parameter processing, conversion and callbacks remain timed. The 1.042× a1/a2 ratio is considerably smaller than the parser-only ratio, and its paired round ratios range from 0.861 to 1.424. It is not evidence of a large new improvement in complete invocation over the previous release.

Small differences need the same restraint. One-option construction measured 1.020× relative to Click; one-option invocation measured 0.973× relative to Click and 1.012× relative to a1. Their sample ranges overlap substantially. The nested-command median remains slower than Click at 0.886×, despite a 1.096× ratio relative to a1.

Affinity kept the measured workers on CPU 0, but frequency was not locked and no frequency readings were available. The host's one-minute load observation rose from about 0.46 to 1.33. Shared-host activity, scheduling, file caches and GC can affect the run; balanced implementation order reduces one source of bias without removing those conditions. Hash seeds also vary across isolated Python processes. No statistical significance claim is made for the small median differences above.

The build-target difference is another attribution limit. Comparing the published a1 manylinux_2_17 wheel with a host-built a2 manylinux_2_34 wheel measures their delivered behavior under this interpreter, including build differences. Component-level attribution and portability require their own comparisons. The historical report and this local run remain intact alongside the separate release-CI result below.

Independent release-CI measurement#

The second run used the release build environment and a different host and Python version. It confirms the direction of the large parser improvement over a1, the large full-invocation advantage over Click, and faster wrapping. It does not reproduce the local 1,000-option parser advantage over Click: the CI median ratio is 0.975×, versus 1.236× locally. The two runs are retained separately because a change of processor, interpreter and build environment prevents attributing that difference to any one factor.

Reusing parser structure#

A parser schema is the Rust representation of option spellings and argument consumption rules. Each command or parser retains at most its most recent owned schema. Before reuse, the binding reads the current definitions and compares their structural fields. Matching definitions reuse the schema; changed definitions produce a replacement. This removes repeated construction of the same owned names and lookup tables while keeping definition validation inside each measured invocation. The implementation is in plan.rs.

The following diagram shows the schema decision within one invocation. Both branches use fresh parsing state.

mermaid
flowchart TD
    A["Current parameter definitions"] --> B{"Match retained schema?"}
    B -->|Yes| C["Reuse owned schema"]
    B -->|No| D["Build replacement schema"]
    C --> E["Parse with fresh call state"]
    D --> E

The retained schema contains Rust structural data. Defaults, environment values, contexts, callback results and Python application objects remain outside it. Parameter registration, parser actions, conversion and callbacks continue through the current Python methods. These boundaries let an application change an alias, arity, callback or type method between invocations without reusing an earlier result. Reentry creates separate invocation state. The schema tests and command mutation tests exercise these distinctions, including copying and pickling a warmed command.

Parameter ordering retains the same live Python behavior at its extension points. For exact lists containing at least 512 declared parameters, ordinary CPython objects may use a guarded Rust ordering operation. It records each parameter's first invocation position in a lookup table, then performs a stable sort. This avoids repeated linear list.index searches; the complete operation is not claimed to be linear, since sorting can require O(n log n) work. Smaller lists, custom protocols and PyPy use Python's sorted and index operations. The ordering regressions cover repeated object identities, equality, eager getters and custom containers. This selection is part of the timed invocation rather than an excluded preparation step.

Input ownership and Python adapter work#

The native binding borrows an ordinary argument's interpreter-provided UTF-8 buffer for the duration of the call. It retains the Python owner and records argument indices so that an existing argument can be returned with its original identity. Strings containing surrogate code points use a reversible surrogatepass representation. Preparing an interpreter's UTF-8 representation, handling surrogate strings and creating Python results can still allocate. The native boundary tests cover Unicode, surrogates and distinct empty string subclasses.

The Python adapters also avoid work whose result is already known. Built-in type selection uses identity checks and reads the current public type singleton on each call. An exact string can pass through string conversion unchanged; string subclasses continue through their Python conversion methods. Plain text width and ANSI removal avoid a native call when their guarded conditions hold, and formatting wrappers retain observation of replaced native functions. These changes are covered by surface regressions.

Help preparation keeps its common single-line path small. It imports inspect only when the running standard library is needed to determine the result, including the whitespace behavior that differs between Python 3.12 and 3.13. Styling and help-table assembly reduce temporary helper objects while preserving output and callback evaluation order. Integer conversion continues to use Python integers, with the same arbitrary precision and current custom conversion methods described in the architecture.

These mechanisms explain which work changed. A complete version comparison measures their combined effect together with parsing, binding and Python execution. Assigning a measured percentage to one mechanism would require a separate component comparison.

What the benchmark measures#

Every workload uses the same public Python entry point and checks its result across all three implementations. The driver retains construction, repeated use and fresh-process execution as distinct boundaries. The full workload definitions are in compare.py.

Boundary Sizes Work inside the measurement

Reused parser All four sizes parse_args, a fresh argument-list copy, definition validation, parsing and parser actions
Warm command invocation All four sizes Command.main, context creation, parser setup, conversion and the command callback
Warm help rendering All four sizes get_help, help assembly, widths and wrapping
Nested command One parent and child Group resolution, child invocation and result handling

The warm invocation reuses an already-created command. Its schema validation and Python hooks remain timed; command construction has its own row. Fresh-process rows include construction and startup, so they also show whether a change helps a CLI that runs once and exits. The fixed command callbacks sum converted integer values. Application-specific I/O, interactive prompts and expensive business callbacks need additional application measurements.

Reproducing a formal comparison#

Build the candidate from a frozen checkout. The following Linux example reproduces the protocol and uses a dedicated output directory so that the wheel argument identifies the intended candidate:

sh
maturin build --release --locked --out dist/benchmark-candidate
python benchmarks/compare.py \
  --candidate-wheel dist/benchmark-candidate/*.whl \
  --iterations 1000 --repeats 12 --seed 20261111 --affinity auto \
  --output reports/benchmarks-0.1.1a2.json

Use the exact wheel filename if the directory contains more than one wheel. Omit --affinity auto on platforms without Linux affinity control. The driver selects the first allowed CPU when that option is used and records the original and selected affinity. Frequency and shared-host activity remain observed conditions rather than controlled constants.

The driver installs the published baseline and candidate into separate environments using the same interpreter and Click wheel. It verifies the published wheel hashes and installed package contents. Formal runs also require the candidate version and Python source files to match the checkout. Reports retain the source commit, native-file hashes, Cargo.lock hash, benchmark source hashes and environment observations. See the measurement protocol for the complete provenance checks and the separate harness diagnostic mode.

Each of the twelve rounds uses a fresh isolated worker for each implementation. Within every six-round block, all six implementation orders occur once, in a seeded order. Each cold workload has its own seeded schedule. The driver checks results before warm timing and compares complete help and wrapping output hashes. It records all wall-time and process-CPU samples, keeps normal garbage collection enabled and verifies the package snapshots again after measurement.

The worker processes run outside the source checkout with isolated Python. Operating-system caches are not flushed, and the order of workloads inside a worker remains fixed. The report records these conditions. A quiet local measurement interval excludes concurrent project builds and tests, while the retained host observations describe activity outside the project's control.
