Measured performance: 0.1.1a3

Published preview: zclick 0.1.1a3 is available from PyPI and GitHub Releases. The published tag points to 9afcc7537212563f66a5d99c9f08f99bfa692731; release validation records all 61 workflow jobs succeeding. Public installation verification confirms the published package separately from the benchmark environments. The known subinterpreter compatibility gap remains open.

Two independent Linux runs compare the measured a3 build with fixed Click 8.5.1 and the published zclick 0.1.1a2 wheel. The local run uses CPython 3.12.14 at commit 2a9e2c3; release CI uses CPython 3.14.10 at 9afcc75. Both hosts identify as AMD EPYC 9V74, but their interpreter, operating system and build environments differ. Each result is kept as its own twelve-round experiment.

Small full invocation improved relative to a2 on both runs. One-option Command.main ratios are 1.079× locally and 1.097× in CI; the nested-command ratios are 1.166× and 1.143×. The larger version changes are in reused parsing: one option measured 1.615× and 1.674× relative to a2. These results do not establish a universal large improvement in complete applications.

The comparison with Click depends on the workload and environment. One-option parsing is slower locally (0.890×) but slightly faster in CI (1.023×); 100-option parsing goes from 1.057× locally to 0.872× in CI. Ten-option parsing remains slower than Click in both runs. The 1,000-option full-invocation ratios against Click are 1.776× locally and 2.128× in CI, while their ratios against a2 are only 1.042× and 1.033×. Most of that advantage over Click predates this revision.

Regressions remain visible. One-option help and Unicode/ANSI wrapping have higher median latency than a2 on both runs; ten-option help also regresses in CI. Four of eight complete fresh-process medians are slower than a2 in each run, though the affected cases differ. Import-only medians are almost unchanged locally and differ only slightly in CI. Wrapping is 7.507× and 9.055× faster than Click for the measured input, but its a2/a3 ratios of 0.978× and 0.988× show that this is an existing advantage rather than a new improvement in a3.

The local schema-2 report and release-CI schema-2 report retain every sample and distribution identity. The published a2 wheel was measured again alongside the candidate in each run. The a2 report and a1 report retain their original historical results. An earlier local candidate run predates the PyPy import correction and is superseded by the fixed local run. Its samples are not pooled with either new run, and timing differences between the two local runs cannot be attributed to the import correction alone.

Ratios mean reference median time / candidate median time. Above one means lower candidate latency; below one means higher candidate latency. A ratio of 1.10 means approximately 9.1% less time, not 10% less time. What changed and what the measurements cover#

The main change reduces the number of Python-to-Rust calls in reused parsing. The parser previously validated its current definitions and then entered native parsing separately. The new entry point performs those operations in one call while preserving publication of the owned plan and the order of normalizer lookup, Python state construction, flag evaluation and resource release. Dynamic hooks still execute. This mechanism is documented in the architecture and implemented in plan.rs and parser.py. The experiment compares the complete distributions; it does not isolate the number of microseconds contributed by this change alone.

Smaller changes reduce repeated work without caching application results. The binding reuses a finite set of literal protocol names such as process and nargs; user-defined names and values remain owned. Exact lists of parameter definitions use a live cursor, so mutation during an attribute lookup remains visible, and list subclasses keep their Python iterator protocol. Each zclap candidate command uses one-argument presence storage, while successful matches still require zclap's event and final validation. These changes are described in the ownership section and parse.rs.

Group dispatch reuses the same fixed protocol names and context-stack push performs one thread-local lookup. The implementation continues to use threading.local: an attempted direct _thread import was reverted to keep the pinned upstream light-import behavior. Error-only helpers are imported when needed. Context managers, Python overrides, conversion and callback calls remain observable; there is no cache of default values, environment results, contexts or callback results. The relevant source is dispatch.rs, globals.py and core.py.

This revision also fixes observable help and parameter behavior. It preserves the target's parameter-container identity, help-option cache and dynamic attribute access order, constructor truthiness and duplicate-parameter warnings. Those are compatibility changes, not evidence of a speedup. Their paired regression cases are in test_command_help_protocols.py. The tables retain the help regressions instead of removing this cost from the comparison.

Measurement boundaries#

The driver measures four distinct operations at each of four sizes. Keeping the boundaries separate shows where a parser improvement affects a complete command and where other work dominates.

Boundary Included work
Construct Public option and command construction for 1, 10, 100 or 1,000 options
Reuse parser A fresh argument list, live definition validation, token processing and current parser actions through an already-created parser
Command.main Invocation of an already-created command, including context creation, parsing, conversion, callback binding and return; standalone_mode=False
Render help Public help generation for an already-created command and context
Nested command A group resolving and invoking a child with one integer option and a checked result
Unicode/ANSI wrapping Public wrapping on fixed Unicode and ANSI-containing text with a checked complete output
Fresh-process command or help Interpreter startup, import, construction, invocation or --help, output capture and exit

Each warm worker starts in an isolated interpreter with -I, outside the source checkout. Its imports and file hashes are verified before and after measurement. Every round starts a new worker per implementation; each six-round block contains all six implementation orders once. Cold workloads have their own balanced order schedules. The warm driver checks and retains full help and wrapped-text hashes, parsed values, option object identity and callback return values across implementations. Cold-process output is also validated by the driver, but the report does not retain a separate stdout hash for every cold sample. The complete method is in the protocol and compare.py.

The two small full-invocation improvements are variable. One-option invocation is faster than a2 in 11 of 12 paired rounds and the nested case in all 12. The a3 nested-case CV is 8.76%, and its paired a2/a3 range is 1.049–1.335. The 100-option help CV is 33.28%; its slowest retained sample is 0.830 ms. One-option full invocation also has a CV of 20.78%, so its favorable median must be read alongside the wider observed range. No slow sample was removed to improve a median or range.

The host is shared and its frequency was not locked. The observed one-minute load changed from 0.465 to 0.886; no CPU-frequency readings were available. Pinning the measured processes to CPU 0 limits migration but does not isolate them from other activity. Garbage collection stays enabled, operating-system caches are not flushed and Python hash randomization varies between isolated processes. Workload order inside each worker is fixed, so balanced variant ordering does not remove every carryover effect.

Scope of the conclusions#

Both sets of measurements test repeated synthetic option lists, a small nested command and a fixed wrapping workload. They include bindings and context costs at the named boundaries, but they do not represent interactive prompts, filesystem work, completion, expensive application callbacks or every custom subclass. A user's elapsed time also includes their own work. There is no basis here for a claim that every Click application becomes substantially faster after changing its imports.

The comparison is with both a fixed behavioral reference and an actual published zclick release. It is not a component ablation: changes in call boundaries, protocol-name reuse, zclap setup and compatibility corrections are measured together. Their individual causal contributions cannot be read from the tables. The substantial wrapping and large-command advantages over Click predate this revision, while the a2 comparison exposes the smaller new changes.

Runtime correctness remains a separate requirement. The performance worker checks its outputs, not the entire Click API or all platform behavior. The earlier PyPy import failure was corrected before these frozen runs, but the CPython measurements do not themselves validate PyPy or the complete release matrix. The project's declared main-interpreter restriction also remains an unfinished compatibility item in COMPATIBILITY.md; benchmark success does not remove it. Publication and completed validation do not establish unrestricted Click compatibility; the release manifest explicitly retains that incomplete status.

Five-question self-review#

  1. Contribution: Is this a new large speedup everywhere? No. The strongest relative version change is reused parsing at small sizes; complete invocation improves more modestly and several operations regress.
  2. Clarity: Can a reader tell which work each number includes? Tables 2–8 separate construction, parser reuse, warm invocation, help and complete process startup; units and reference direction are explicit.
  3. Experimental strength: Are the controls immutable and the reversals visible? Both runs retain distribution, source and native hashes, all eighteen warm cases, all eight cold cases, raw samples and paired ranges. The local and CI results are separate; neither is selected because it is faster.
  4. Evaluation completeness: What evidence is missing? Final release validation is linked separately from these measurements. Component ablation and application-specific measurements would be needed for stronger causal or general claims. Two environments are reported, and the earlier candidate's data remains separate.
  5. Design soundness: Is less work obtained by removing public behavior? The design retains live definitions, dynamic Python methods and context cleanup. Its behavior must pass the separate compatibility checks; the corrected PyPy import was checked in the separate release matrix, outside this CPython performance experiment. Subinterpreter compatibility remains unfinished.

Reproducing the local comparison#

Use a separate clean checkout of the recorded commit and the same CPython interpreter for both controls and the candidate. The protocol validates the candidate's version and Python file hashes against that checkout. The baseline is selected by baseline-lock.json, which pins the published a2 and Click wheels. The earlier a1 lock remains available for reproducing its own reports and must not be silently substituted here.

sh
maturin build --release --locked --out dist/benchmark-candidate
python benchmarks/compare.py \
  --candidate-wheel dist/benchmark-candidate/zclick-0.1.1a3-cp310-abi3-manylinux_2_34_x86_64.whl \
  --iterations 1000 --repeats 12 --seed 20261111 --affinity auto \
  --output reports/benchmarks-0.1.1a3.json

The example wheel filename is the one measured on this host; use the actual filename produced by the local build, and pass exactly one candidate. On Linux, --affinity auto selects the first CPU in the allowed set. Omit affinity control where it is unavailable and retain that difference in the report. Run timing without competing local builds or tests, preserve the complete JSON and review its source, native hashes and sample ranges before interpreting results. Keep later builds or platforms in separate immutable timing records.
