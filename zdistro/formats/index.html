Format backends and verification

zdistro delegates package construction to the ecosystem's own tools. A format backend has four responsibilities: declare prerequisites, describe a plan, produce an artifact, and verify that artifact. Language compilation happens before file staging; cross compilation remains a language-toolchain setting.

Built-in formats#

Target Builder / required tools Verification performed
deb dpkg-deb Package/version identity and payload listing
arch makepkg, fakeroot, pacman, bsdtar Native package inspection and .PKGINFO, .BUILDINFO, .MTREE
zip, tar-gz Python standard archive libraries Member boundaries, readable archive; ZIP CRCs
crate cargo package Cargo's default unpack/build verification, normalized manifest identity
wheel python -m build --wheel Core metadata and every wheel RECORD digest/size
sdist python -m build --sdist Source distribution archive and PKG-INFO identity
npm npm pack --ignore-scripts Tar structure and package.json identity
extension, xpi ZIP library Root manifest, required fields, local scripts/pages/icons, ZIP CRCs
pkg macOS pkgbuild, pkgutil Expand native metadata and payload without installing
dmg macOS hdiutil Image integrity and format inspection without mounting
msi Windows WiX 4+ CLI Native MSI database decompilation
msix Windows SDK MakeAppx ZIP/block-map metadata and native unpack
apk Android AAPT2 + platform android.jar, or existing Gradle project AAPT2 parsing and actual application ID/version matching
aab AAPT2 or Gradle project, Java and bundletool Bundle module validation and actual manifest identity/version matching
docker Docker Buildx or Podman Docker/OCI archive references and OCI blob digests/sizes

These are artifact checks. Installation/upgrade behavior, application behavior, code signing, notarization and store review require their own workflows and are not marked complete by an artifact receipt.

Linux packages#

Debian and Ubuntu packages are created with dpkg-deb --root-owner-group --build. zdistro generates DEBIAN/control from the package metadata and records runtime dependencies from targets.deb.depends. This follows the native tool's binary package directory contract. See dpkg-deb.

Arch packages use a generated PKGBUILD whose package function copies the staged files. makepkg generates the ALPM metadata and compressed archive. The backend uses --nodeps because language builds and their tool checks have already been performed before staging; declared runtime dependencies remain in the package. No dependencies are installed into the host. makepkg requires an unprivileged user. The output uses .pkg.tar.gz, a native makepkg-supported compression choice. BUILDDIR is confined to this build's private directory, overriding host-wide temporary-build settings without changing them. See makepkg, ALPM package contents and PKGINFO.

architecture = "all" (Debian) and architecture = "any" (Arch) are suitable for architecture-independent payloads. Select the actual architecture for compiled binaries. Package metadata does not cross-compile the executable.

Python, Rust and JavaScript#

Python artifacts use the normal PEP 517 frontend and the project's declared build backend. Install build in the Python environment that runs zdistro. Isolation is enabled by default; isolation = false is available when the user has already provisioned the backend. Metadata is read from the built archive, not synthesized by zdistro. See Python packaging flow and wheel format.

Cargo source packages are made with cargo package, including its normal verification build. The normalized Cargo.toml must match the unified package name and version. Select a single package project for each target. See Cargo package.

npm packages use npm pack --ignore-scripts; explicit language builds can run npm run <script> before native packaging. build.install = true runs npm ci --ignore-scripts in the private project copy first. Source manifests and lockfiles are preserved. See npm pack.

Browser extensions#

extension creates a ZIP with manifest.json at its root. xpi uses the same WebExtension layout with an XPI suffix. The validator checks manifest version, name/version and declared local script/page/icon resources. Browser API compatibility and store policy validation remain browser-specific; run that browser's linter and runtime tests in your build recipe when required.

Chrome accepts an extension ZIP for upload. Firefox distribution normally involves Mozilla signing. The built-in XPI output is unsigned. See Chrome preparation, WebExtension manifest and Mozilla extension signing.

macOS and Windows#

PKG and DMG adapters run on macOS. PKG files use the declared package identifier and install the staged relative paths under /. DMG files use a read-only UDZO image. They are left unsigned for an explicit signing/notarization workflow. Apple describes the distinction between containers, signing and distribution in Packaging Mac software.

MSI packages are generated from staged files through WiX's native schema and CLI. The installer uses a per-machine Program Files directory. Verification decodes the MSI database; it does not perform an installation or the full ICE suite. See WiX CLI and WiX validation.

MSIX requires a real staged Windows PE executable at targets.msix.executable. The backend generates a desktop manifest, neutral template icons, block map and package through MakeAppx. Specify the correct publisher and identity for later signing. The generated manifest requests runFullTrust for a Win32 executable. See MakeAppx.

Android#

Android receipts record the actual application_id, version_name, and version_code read from the artifact. targets.apk / targets.aab can set these expected values explicitly; application ID otherwise uses the explicitly declared package.identifier, and version name uses package.version. A mismatch fails the build and re-verification. This also checks independently configured Gradle application IDs and flavors; the package display name is never used to guess an ID.

The APK template builds a small no-code Android package with AAPT2 and an installed SDK platform. For an existing Android app, select mode = "gradle", point project at its source, and declare the task and relative output artifact. The Gradle wrapper must be complete. SDK paths come from ANDROID_HOME or ANDROID_SDK_ROOT; platform = "android-35" can choose an installed platform. No SDK is downloaded or configured by zdistro.

AAB can link the manifest/resources as protobuf through AAPT2, assemble the standard base-module ZIP layout, and call bundletool build-bundle. Existing Gradle apps can use mode = "gradle" with a task and output path. Both routes validate the resulting bundle with bundletool. Provide bundletool_jar or the BUNDLETOOL_JAR environment variable. Missing Gradle projects, tools and SDK components are reported by doctor. The checked-in CI reuses its existing SDK and provisions a pinned, checksum-verified bundletool JAR in the workspace. It builds actual APK/AAB artifacts and records prerequisite checks; the contract tests also exercise the missing-SDK failure. See Android command-line builds, AAPT2 and bundletool.

Containers#

Docker uses an explicit Buildx docker or oci exporter to write an archive. Both formats need a driver that supports archive export, such as docker-container. The classic docker driver lacks these exporters unless its worker reports the containerd snapshotter. doctor inspects the selected builder without bootstrapping or creating it and reports the missing capability before a build begins. You can create a dedicated builder once:

sh
docker buildx create --name zdistro-packages --driver docker-container

Select it explicitly in the manifest; the global default builder stays unchanged:

toml
[targets.docker]
project = "container"
engine = "docker"
builder = "zdistro-packages"
archive = "oci"
files = []

When builder is omitted, Docker's existing selection, including BUILDX_BUILDER, applies. The formal Linux workflow creates and removes its own builder in the disposable runner. See Docker/OCI exporters and Buildx inspection.

Podman builds a unique local image, saves the selected archive format and removes only that build's unique tag. No image is pushed to a registry by the backend.

Verification follows archive references and validates SHA-256/size for recursively referenced OCI blobs using bounded reads. Docker image archives are checked for a valid manifest, configuration and uncompressed layer digests. See Docker exporters, Docker save and the OCI image layout.

Extension contract#

A custom backend declares hosts, tool names, literal build argv arrays, an output path and literal verify argv arrays. Success requires both command groups and a nonempty regular artifact inside the assigned output directory. Receipts label these results recipe, keeping the supplied verifier's scope explicit. Add new language tools through build.kind = "command"; JSON/TOML and compression stay with standard libraries and ecosystem tools.

Staging supports regular files and rejects escaping paths, file collisions and unsupported links. Source trees containing application-specific symlink layouts can use an explicit native recipe. Build scripts remain executable project code; this utility provides isolated working directories, not an operating-system sandbox.
