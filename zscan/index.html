zscan

在字节切片中正向或反向查找字节和子串，并返回原始位置。

Byte and substring search with no dependencies, no allocation and an always no_std library. Rust 1.70 or newer; MIT licensed.

toml
[dependencies]
zscan = "0.1"

The API consists of four functions and one borrowed searcher:

rust
use zscan::{find, rfind, find_byte, rfind_byte, Finder};

assert_eq!(find_byte(0, b"ab\0cd"), Some(2));
assert_eq!(rfind_byte(b'a', b"aba"), Some(2));
assert_eq!(find(b"ababa", b"aba"), Some(0));
assert_eq!(rfind(b"ababa", b"aba"), Some(2));
let finder = Finder::new(b"aba");
assert_eq!(finder.find(b"xxaba"), Some(2));
assert_eq!(finder.rfind(b"ababa"), Some(2));

All inputs are byte slices, including NUL and invalid UTF-8. Returned positions are byte offsets in the original haystack. An empty needle matches at 0 forwards and haystack.len() backwards. An overlong needle returns None.

Complexity and implementation#

Byte search takes O(n) time. Substring search takes worst-case O(n + m) time and O(1) extra space, where n and m are the haystack and needle lengths. Finder::new takes O(m) time, borrows its needle, and caches fixed-size metadata for both directions. It never copies or reverses the input. A Finder can be shared between threads; searches do not mutate it.

Short haystacks avoid preprocessing. Longer searches filter candidate starts using two needle bytes, then verify the full candidate. A failed verification can replace an unhelpful probe with the first mismatching byte. Verification spends a single search-wide budget: initially 2m, replenished only by newly skipped positions, with m charged per candidate. When that budget is exhausted, search falls back once to Two-Way. This bounds verification work by O(n + m), including repeated and periodic data.

CPU support and safety#

Target Generic build
x86-64 AVX2 after cached CPUID, OSXSAVE and XCR0 checks; otherwise SWAR
AArch64 with target-guaranteed NEON NEON
Other targets Portable SWAR/scalar

The x86 AVX2 path aligns its byte-scanning bulk loop and uses complete, in-bounds overlapping vectors at the slice boundary. It also uses SSE2 for 16-byte candidate ranges. No vector load crosses either end of a supplied slice; unaligned slices are supported. Safe public functions require no caller feature detection. A build using -C target-cpu=native or explicit target features must run on a compatible CPU and OS, as with any Rust binary built with those flags. No std feature detector, allocation, FFI, build script or third-party dependency is used by the library.

Unsafe code is confined to architecture intrinsics and their private checked dispatch; each block records its feature and access preconditions. Linux protection-page tests use libc FFI in the test executable only.

Tests include independent naive references, exhaustive small alphabets, seeded random inputs, every short match position, binary data, offsets, SIMD tails, direct scalar/vector comparisons, and guarded pages. CI runs stable and MSRV on x86-64 and AArch64, fmt/Clippy, native builds, scalar Miri, and bare-metal thumbv7em-none-eabi / aarch64-unknown-none library builds.

Benchmarks#

The isolated comparison project pins memchr 2.8.3 and memx 0.2.2. The fixed protocol includes 607 short, binary, structured-text, alignment, tail, and adversarial workloads. One-shot timing includes preprocessing and dispatch; Finder construction and reuse are measured separately. All measurements are ns/op, including early returns. Raw samples, source snapshots, hashes, build settings and failed comparator answers are retained. See baseline correctness notes.

On the recorded Xeon Platinum 8573C / Rust 1.99.1 generic build, the geometric mean speedups against the fastest correct baseline in each case were:

Workloads One-shot substring forward One-shot substring reverse
Short (238 cases) 1.21x 1.68x
Typical binary (195 cases) 1.34x 7.67x
HTTP / JSON / logs (48 cases) 1.92x 5.27x

The overall 2x research target was not met. Typical byte searches were 0.98x/0.91x the fastest forward/reverse baseline, and some short/reused searches regressed. These repeated-buffer, warm-cache measurements on shared hardware are observations, not a universal performance guarantee. The current full report includes all cases, slower results and native builds. The round-2 review compares the previous implementation with matched memchr controls, explains the warmup-calibration correction, and retains regression investigations. The earlier component ablations remain available with their original source snapshots; they were measured before this revision.

Release#

The Release workflow supports current, patch, minor, major, and custom version selection, plus existing-tag recovery. Use Actions → Release → Run workflow on main, or commit an explicit .github/release-request.json request as described in the maintenance guide. A bump updates the manifest and both lockfiles, then atomically pushes the version commit and its immutable tag. Existing vX.Y.Z tag pushes are also supported.

The workflow checks the tag's exact commit through the full CI matrix, verifies the package contents, packages and dry-runs before publishing. Only the publish step receives the repository Secret CARGO_REGISTRY_TOKEN. An exact crates.io archive checksum must be confirmed before a GitHub Release is created. Ambiguous upload errors are checked against the registry before any manual recovery; an existing version is never overwritten.
