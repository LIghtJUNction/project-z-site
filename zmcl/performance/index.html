条件、显示服务与换页#

在2026-11-20 15:48:13–15:50:49（Asia/Taipei）运行，Linux x86_64、1120×760窗口、私有Xvfb、zgpui原生CPU后端。每轮先预热20秒，再记录11个一秒间隔的静置样本；随后6秒内以60 Hz请求360次Expose，事件可能合并，并记录重绘后静置。没有清空系统缓存，没有启动Minecraft/Java。

三轮活动样本完整。六项管理流程共有2,938条样本，其中129条包含已退出或不可读的相关进程；这些条目保留，完整树中位数和完整CPU总量为 null，管理内存状态为 needs_review。功能六项通过与测量完整性分别判断；未知进程的值不作为零。

显示服务单列：启动前Xvfb RSS为37,620–37,900 KiB；运行时静置RSS增量为1,248–1,512 KiB，PSS增量为1,061–1,269 KiB。管理流程Xvfb RSS/PSS中位数增量为584/270 KiB。显示服务不是应用子进程，其绝对值、before/during差值及负增量都保留在汇总中。优化未增加常驻后台绘制进程。

第二轮重绘后静置发生换页：该阶段应用PSS中位数为3,301 KiB、SwapPss中位数为1,336 KiB，逐样本相加后中位数为4,637 KiB；Xvfb SwapPss为8,432 KiB。不能把这一轮驻留下降视为优化收益。空库idle、drawing和管理阶段已读取到的SwapPss为零；缺读仍是未知。

33个宿主快照都观察到外部Cargo/Rustc等任务。MemAvailable最低2,009,508 KiB，memory PSI avg10最高some=4.34、full=3.87。这是共享开发机的限定实测，不是独占安静机器上的普遍性能结论。

为什么下降，仍缺什么#

原版本的OpenGL软件驱动和字体匹配状态占据了大量驻留内存。本版直接使用CPU绘制，字体匹配后释放临时状态，并在X11复制帧后释放客户端像素页；重绘仍需要完整四字节像素表面，1120×760即3,404,800字节。原生实现与生命周期检查见上游源码。

首次CPU接入开发构建 fcc214bf / 二进制 99ea0d70… 的同类活动脚本基线为RSS/PSS 17,560/9,846 KiB。当前构建的空库值更低，但两批共享宿主压力不同，不据此给出通用节省倍数。后续重点是字体初始化峰值、绘制期间的像素与文字缓存，以及管理任务的Python常驻工作集。仅降低首页或把操作移至后台，都不能完成完整口径目标。

复测入口为 scripts/bench_gui_activity.py 和 src/gui/manage_smoke.py --memory-output，先固定实际构建版本、源码提交和二进制哈希，再运行默认参数。完整复现命令及数据字段在脚本 --help 和当前汇总中。

v0.1.0 与 XMCL 的历史对照#

以下保留v0.1.0原始身份、软件图形环境和固定XMCL v0.73.1比较；不改标为本次0.1.1的测量。

本次记录对应 zmcl 源码 0337762 和 XMCL 官方 0.73.1 Linux x64 发行版。2026 年 11 月 20 日，在同一台 Linux 开发机上，使用同一份 schema 4 脚本，各运行三轮默认空首页。zmcl 的主程序为 1,412,176 bytes；空闲 PSS 的三轮汇总值为 89,946 KiB（87.84 MiB），XMCL 为 376,722 KiB（367.89 MiB）。zmcl 原始样本 · XMCL 原始样本

这些数值只描述本次软件渲染环境中的默认首页。 两款应用开始测量时，主机可用内存分别为：XMCL 1,894,756 KiB，zmcl 6,492,216 KiB。XMCL 样本存在明显换页，两个默认首页的内容也不同。以下表格同时保留驻留页、换出页和合计值，不据此推导相同功能下、所有机器上的性能倍数。zmcl 仍在补齐功能，当前范围见功能矩阵。

PSS+SwapPss 是“驻留和换出页面的合计，非实际物理 RAM”。 它是在每个采样点内先相加，然后取轮内与轮间中位数；不能直接相加表格中已取中位数的两行。这里的合计也不代表总分配量、峰值或系统整体内存使用。派生汇总与计算口径

zmcl 三轮观察窗内的 CPU ticks 都没有增加。内核 CPU 计数频率为 100 Hz，每 tick 为 10 ms，因此这里的 0.00 秒表示有限观察窗内未观察到计数增加，不表示任意时段都没有 CPU 消耗。CPU 单核占用率由 CPU 时间除以各轮实际经过时间计算；不是全机 24 个逻辑 CPU 的总百分比。

窗口出现与首帧#

同一脚本以约 250 ms 间隔轮询 X11 窗口，记录“窗口被发现”的时间。zmcl 三轮为 292.377、296.835、296.322 ms；XMCL 为 1,621.568、3,334.413、1,066.178 ms。各自中位数为 296.322 ms 与 1,621.568 ms。这是轮询发现窗口的时间，受到调度和轮询粒度影响，不是首个可交互画面时间，也不能视为严格冷启动成绩。

zmcl 另有进程内首帧标记，本次为 277、271、298 ms。它从 GUI 入口计到第一帧提交，起点与外部窗口检测不同；XMCL 没有对应标记，因此不对这一数值作跨应用比较。操作系统缓存没有清空，顺序运行可能影响时间。

内存与 CPU 采样方式#

RSS 表示驻留页；PSS 对共享页按共享进程数分摊。SwapPss 记录换出页的相应份额。多进程 RSS 直接相加会重复计入共享页，所以资源比较同时展示 PSS、SwapPss、RSS 和进程数。Linux 内核 /proc 说明

脚本读取每个观察到的进程的 smaps_rollup。读取失败的样本会保留失败标记，不参与完整内存样本的中位数。CPU 身份由 PID 和 starttime 组成，累计 utime+stime 增量。只有采样点身份集合稳定、读取成功且计数没有回退，才发布完整 CPU 值；否则返回 null，并单独保留共同存活进程的观察值。两个采样点之间产生并退出的短命进程可能漏记，因此本协议不代替安装、下载或游戏运行阶段的持续跟踪。

每轮开始和结束都校验可执行文件 SHA-256。最终脚本仅选择 100–199 号显示，跳过任何已有锁或 socket，确认 Xvfb 锁中的 PID 属于本轮进程后才使用；每轮使用新的空授权文件，不读取现有桌面授权，不修改已有显示的访问策略。本次六轮均使用释放后可复用的 :110。

复现#

先准备已经校验的两个应用。脚本需要 Linux /proc、Python 3、Xvfb、xdotool、glxinfo 和 ImageMagick import。下例只展示测试入口；XMCL 路径替换为解包后的官方 ELF，输出路径选用新的空目录。

sh
nice -n 10 python3 scripts/test_bench_linux.py

nice -n 10 python3 scripts/bench_linux.py \
  --app xmcl --binary /path/to/xmcl \
  --version 0.73.1 --revision v0.73.1 \
  --output .test-evidence/reproduce/xmcl \
  --trials 3 --warmup 20 --samples 11 --interval 1

nice -n 10 python3 scripts/bench_linux.py \
  --app zmcl --binary target/release/zmcl \
  --version 0.1.0 \
  --revision 033776287ab10aab90f46fd5b65309fecb9b8711 \
  --output .test-evidence/reproduce/zmcl \
  --trials 3 --warmup 20 --samples 11 --interval 1

五项脚本回归验证了已有子进程的后代遍历、稳定集合的 CPU 增量、进程进入与退出、PID 复用、读取不完整时的判断。它们验证采样代码的关键边界，不消除共享主机与图形后端的实验限制。正式原始记录共 66 个完整样本，未在结果中挑选轮次。

游戏启动后减少常驻进程#

普通 CLI 的 launch 子命令在启动游戏并返回 PID 后退出。GUI 用户也可以显式启用：

sh
zmcl gui --exit-after-launch

该选项只在游戏 launch 任务成功、输出包含有效正 PID 后让 GUI 正常退出；安装、账号任务、错误、取消和不包含真实 PID 的输出不会触发退出。游戏在独立进程组中继续运行，日志写入实例日志目录。实际功能验收观察到 GUI 退出码为 0，游戏 Java 在其退出 10.162 秒后仍存活；该次记录没有把“Java 存活”表述为“已到达主菜单”。生命周期证据

本页所有 GUI 基准均使用默认保持打开的状态。退出后的启动器零常驻进程不与仍打开的 XMCL 作比较。
