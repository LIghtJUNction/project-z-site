XMCL compatibility record

0.1.4 distribution and installation#

The source connects the fixed zdistro 0.1.0 packager to Linux tar.gz/DEB and native Windows ZIP preparation. Distribution instructions describe the artifact and runtime-dependency checks. Availability and native acceptance belong to each published release; no macOS application package is provided.

Settings now shows the running launcher version, platform, executable location and advisory installation source. A manual Check for updates action and zmcl update check --json inspect official GitHub releases, compare semantic versions, and select packages for the current OS and architecture. A newer local build is reported as ahead of the published package. Failures can be retried, and release links can be opened or copied; installation remains with the selected installer or package manager.

The portable installer reports the installed version, prefix, direct launch command and same-prefix update command. If PATH selects another zmcl, it identifies both copies. Validated distribution metadata and the generated installation receipt join the existing strict file/digest manifest. Upgrades refuse modified or unmanaged installation files; removal preserves modified files and game data. Windows installations use bin/zmcl.exe, and user-facing Python requirements remain 3.8+.

The wrapper-to-installer roundtrip uses a real small ELF, the fixed zipapp and private prefixes with spaces. It verifies distribution/installation metadata, installed file digests, removal and synthetic game-data preservation. The Windows distribution workflow records its native build, install, window and removal results separately. These source-level improvements do not relabel the earlier application, account, game or memory evidence below.

0.1.3 management and distribution iteration#

The 0.1.3 report records source 9ef89bb92d46d324172d6ea8b13054c81434e178, 97 Rust tests, 51 affected Python tests, real CLI file roundtrips, two six-flow native GUI observations, and another six-flow check of the AUR-installed binary. GitHub v0.1.3 and AUR 0.1.3-1 are published; normal host upgrade and public-index readback passed. Helpers load modules on demand, backup list entries release full archive indexes between inspections, and JSON output avoids a complete encoded duplicate. This reduces observed large-backup query peaks in the fixed paired fixture; the complete GUI below-10-MiB target remains unmet. No new Windows/macOS, real-account or game/server-launch acceptance is inferred, and the fixed XMCL baseline and feature gaps below remain unchanged.

0.1.2 iteration#

The implementation and evidence report records application source e86b5841532ef04cc74cea5585ae396150452408, 97 Rust tests, strict Clippy, native creation/management fixtures and explicit Windows/macOS limits. Archive, metadata and Horizon helpers now share actual Python 3.8+ discovery, isolated UTF-8 execution and retry after a missing interpreter is installed. Windows background helpers suppress extra console windows while preserving output/error streams. Large-library and empty-window measurements identify their separate pre-release candidates; they are not relabelled as final 0.1.2 performance measurements.

zmcl targets the functional scope of XMCL v0.73.1, commit aeb52403945f017a17f4014cb6542f73fa47dd15. The fixed service interfaces define the comparison baseline. The official feature catalogue provides product context and may describe newer upstream work. Full coverage remains a development target; the gaps below remain part of the acceptance work.

This record separates implementation, local fixtures and live results. Implemented identifies a reachable code path. Fixture accepted identifies tests with controlled files, synthetic NBT, fake network peers or process fixtures. Live accepted identifies a named provider download, native interface interaction or real game outcome. Each result applies to its stated environment. Build identities, current test totals and sanitized outcomes belong in VALIDATION.md; process-tree and storage measurements belong in PERFORMANCE.md.

Recorded lifecycle acceptance#

scripts/test_lifecycle_cli.py ran 21 recorded real CLI commands in a new isolated data root. Three commands deliberately tested and received protective failures: importing over an existing world, exporting over an existing ZIP, and restoring an instance into an occupied target. The successful commands checked world directory/ZIP/clone roundtrips, backup manifests and pre-restore snapshots, independent writable instance copies, and trash/list/restore.

The source world contains three files totalling 2,111 bytes: generated gzip NBT, an explicitly opaque region fixture and a fixture marker. It is not a game-loadable world. No Java/game/server process or network download is requested. The acceptance establishes command routing, response fields and file preservation; playing and saving a real imported world remains a separate target.

Capabilities still outside the implemented scope#

These remain visible acceptance targets from the fixed XMCL baseline:

  • OptiFine/LabyMod installation; alternate Yggdrasil, Ely.by and LittleSkin authentication.
  • CurseForge/FTB distribution and unavailable-file handling; CurseForge, MCBBS, Packwiz, offline/server-pack workflows beyond the implemented mrpack path.
  • Mod/content groups, optional-dependency UI and creator project/gallery/version publication.
  • World/data-pack editing, chunk visualization and 3D blueprint workflows.
  • Scheduled/remote backups and retention management; remote SSH/SFTP servers, deployment and service credentials.
  • P2P LAN discovery, ICE/STUN/relay traversal and two-client acceptance; Together-specific service integrations.
  • AI crash diagnosis and model-provider/tool permissions beyond basic local diagnostics.
  • Full desktop file associations, shortcuts, notifications and accessibility; themes/backgrounds; controller-only Big Picture and virtual keyboard.
  • Windows Bedrock management; a signed launcher self-update/rollback channel; complete OS/game/loader acceptance.
