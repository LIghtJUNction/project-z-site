Protocol scope

ztty 0.5.2 implements the following subset of public terminal protocols. The shared core is used by Linux, macOS, and Windows; native window integration and its verification status are described separately below. The 0.5.2 release report binds the current release's six-platform acceptance to its source and artifacts.

Text and input protocols#

Protocol / behavior Scope
ANSI / VT controls Cursor motion, save/restore, tabs, scrolling regions, erase, insert/delete, main/alternate screen, DEC line drawing
SGR 16/256/RGB colors, semicolon and colon parameters, core attributes; font shaping and style rendering depend on the frontend
UTF-8 Streaming decode across arbitrary chunks; CJK widths; complete extended grapheme clusters within bounded storage
Kitty keyboard Flags 1/2/4/8/16, event reports, shifted alternatives, associated text, independent screen stacks; the Linux frontend does not supply a base-layout alternative
Mouse DEC 9 (X10)/1000/1002/1003 tracking; legacy and SGR 1006 encoding
Focus DEC 1004
Cursor appearance DECSCUSR block, underline, and bar with steady or blinking variants; DEC private modes 12 and 25
Bracketed paste DEC 2004; bounded paste with control-character sanitization
Synchronized output DEC 2026, DECRQM, retained last frame, 150 ms recovery timeout
OSC 0/2 Window title
OSC 7 Working-directory metadata retained in the model
OSC 8 Cell identity, history retention, underline, explicit Ctrl+click opening
OSC 4/10/11 Color queries; reply with the request's BEL or ST terminator
DSR / DA / DECRQM Implemented state reports; unknown modes report unsupported
Window and cell size CSI 14 t reports text-area pixels; CSI 16 t reports cell pixels; CSI 18 t reports character dimensions
XTGETTCAP TN=xterm-256color, Co=256, Tc; unknown capabilities report failure
X11 clipboard Clipboard and primary selection, advertised text formats, UTF-8 and Latin-1 fallback, bounded INCR receiving
OSC 52 Bounded clipboard requests with frontend policy; Linux enforces visible-view and input-ownership checks
Native Wayland input XKB/compose and text-input-v3 preedit/commit; see Wayland configuration and limits

The shared core retains extended grapheme clusters, including emoji ZWJ sequences, with at most 256 UTF-8 bytes per cluster and a bounded pool; this is separate from font rendering. Width changes reflow retained primary-screen soft wraps while preserving hard line boundaries. Alternate screens retain fixed-grid resize semantics, and history limits can evict content. See the core storage and reflow contract.

Linux GPU text uses HarfBuzz run shaping; the Xft fallback draws Unicode cells without that complete-run shaping path. Linux supports italic glyphs and SGR 5/6 text blink. Cursor blinking remains separate. These capabilities do not establish identical complex-script or emoji presentation across every renderer.

Primary DA uses CSI ? 62 ; 4 c: a VT220-style identification with the Sixel feature field. No other optional DA features are asserted. This also satisfies the minimum response length used by Kitty's graphics probe. Kitty graphics support and transport choices are established by their own queries.

Kitty graphics#

zgraphics implements the bounded image lifecycle: receive image data, store decoded pixels, place an image, and delete its placements or data. zterm frames APC sequences and attaches placements to terminal content. The native frontend composites the resulting RGBA images; no Kitty renderer is embedded.

Feature Implemented scope
Transport Direct PTY data, t=d; base64 encoded. The Linux host also supplies bounded file (t=f), temporary-file (t=t) and shared-memory (t=s) reads
Pixel formats f=24 RGB, f=32 RGBA, f=100 PNG; canonical storage is straight-alpha RGBA8
Compression Optional zlib, o=z, with bounded output
Static actions Capability query a=q, transmit a=t, transmit and display a=T, place a=p, delete a=d
Extensions Linux X11 integrates Kitty animation, Unicode placeholders and relative placements; extension acceptance records GPU and Xft coverage
Transfer chunks m=1 continuation and m=0 final chunk; arbitrary PTY read boundaries; larger single APCs and repeated-action continuation headers from current clients
Base64 endings Padded or unpadded final payload; nonfinal protocol chunks must contain complete groups without padding
Identity Explicit image IDs i, image numbers I, automatic IDs, placement IDs p, replacement under an existing ID
Geometry Source crop x/y/w/h, cell-relative offset X/Y, requested columns/rows c/r, viewport clipping
Scaling Aspect ratio preserved; when both c and r are set, the image is centered within that box
Cursor Placement advances the cursor according to its occupied box; C=1 leaves it unchanged
Layers z >= 0 above text; negative z behind text; z < -1073741824 also behind explicitly colored backgrounds
Deletion Visible placements, ID/number/placement, cursor or cell, row, column, z-index, and ID range selectors; uppercase forms free selected data once unreferenced
Replies Success/error responses for identified requests; q=1 suppresses success, q=2 suppresses all replies; queries do not place or retain images
Content lifetime Full-screen scroll can retain images in history; partial-region scroll moves placements anchored in that region; primary and alternate screens have independent scenes

An image appears only after its final transfer completes successfully. Replacing an image ID removes the old placements; changing a placement ID replaces that placement. Cell metrics supplied by the frontend determine pixel geometry and size replies. Both image IDs and their generation values are used when deciding whether a renderer's cached pixels are still current.

Existing kitten icat clients can emit image payloads larger than 4096 encoded bytes in one APC and use unpadded base64. The streaming receiver accepts that shape while retaining at most a 512-byte header and a 4096-byte encoded staging buffer. It incrementally decodes into a separately bounded pending transfer. This avoids accumulating an entire encoded APC in a general control-string buffer. Client emission behavior can be inspected in Kitty's graphics command writer.

Image limits and recovery#

These are default limits per graphics scene, as defined by zgraphics::Limits:

Resource Default bound
Width or height 8192 pixels
One decoded image 32 MiB
Retained decoded image storage 32 MiB, counting vector capacity
Pending transfer 16 MiB
Stored images 128
Placements 512

Both dimensional and byte limits apply. A nominally permitted width and height can still exceed the decoded-image byte limit. Primary and alternate scenes have separate quotas; these figures are not a process-wide memory ceiling. PNG decoding uses temporary buffers, and frontends retain display resources. The memory accounting section explains those additional costs. Empty scenes allocate no image storage.

PNG headers, chunk lengths, CRCs, and dimensions are checked before decoding; nonessential metadata is removed. Malformed PNG, incorrect pixel lengths, bad base64, unsupported options, and quota overruns are rejected. A pending m=1 transfer does not consume ordinary text between APCs. CAN, SUB, or a new escape sequence can cancel an unfinished APC, so a missing terminator does not trap subsequent escape sequences. Tests exercise valid text, keyboard input, and a new valid image after rejection. The test sources are zgraphics tests, zterm tests, and the graphics acceptance suite.

Remaining boundaries#

Area Current boundary
External Kitty transport The file/temporary-file/shared-memory host reader is Linux-only; macOS and Windows use direct transmission
Image decoding and protocols APNG and ReGIS remain unsupported; Kitty frame animation is a separate implemented protocol
Native Wayland No tabs, splits, workspace containers or runtime reload; desktop scaling and real IME/GPU acceptance remain separate work
Text layout Complex-script and emoji presentation depend on the font and renderer; Xft does not provide the GPU path's complete-run HarfBuzz shaping

Applications should query the required transport and extension capabilities. Successful static-image display alone does not establish full Kitty compatibility.

Sixel#

The shared no_std core accepts ESC P ... q Sixel images, commits only at ST, and reuses the existing RGBA scene and native renderers. RGB/HLS color registers, repeat compression, raster extents, aspect ratio, transparent/opaque backgrounds, color overprinting, and arbitrary PTY chunk boundaries are implemented. Modes 80, 1070 and 8452 control display origin/scrolling, palette scope and cursor placement. Default scrolling starts at the text cursor and ends at column zero on the following text row; display mode preserves the cursor. Details and resource limits are in zgraphics.

Sixel images use the scene's behind-text layer and remain anchored to cell rows. Text writes and partial erases clear intersecting Sixel source pixels; Kitty placements are unaffected. At scaled boundaries, a whole intersecting source pixel is cleared, as documented in the Sixel erasure regression. Partial-region scrolling follows the anchor policy. Shared palettes seed later images; changing a register does not recolor an already completed RGBA image. These limits remain distinct from complete VT340 framebuffer compatibility.

Decoder validation uses the DEC manual, the modern xterm control reference, and an independent libsixel pixel comparison. The measurement records source/binary hashes, chunk sizes, exact pixel results and reference-decoder discrepancies. These decoder results are distinct from the native GUI acceptance below.

Acceptance coverage#

The 0.5.2 release report records successful Verify and native Linux, macOS and Windows jobs on x86_64 and AArch64 for source 6e2ce246b0b50e6b82da99756832feae6e966f21. Each Linux artifact has 22 reports with 312 recorded checks, including 65 Wayland checks, bound to that artifact's ELF. The Linux GPU-path tests use software Mesa; they do not measure physical GPU performance, display latency or general desktop IME compatibility. This documentation update adds no new test execution.

Historical acceptance snapshots#

The reports below retain their original source, binary and test scope. For example, the earlier native record at 2dc6769 passed four Linux x86_64 GUI suites and 25 Windows x86_64 checks, while its ARM64 gates failed and macOS completed eight protocol checks. Those historical outcomes are not the current 0.5.2 release status.

The GUI suite has passed 12 checks under an isolated Xvfb/X11 server, as recorded in the GUI result: legacy keyboard input; Kitty disambiguation; all five Kitty flags with modifier, repeat, and release events; resize and SIGWINCH; ASCII/CJK selection and clipboard; bracketed paste with control stripping; a 139,264-byte paste under backpressure; SGR mouse input; Shift gesture ownership; explicit OSC 8 opening; configured ARGB background and cursor rendering; and synchronized output across writes and Expose events. The large-paste assertion includes the 12 bytes of bracketed-paste delimiters, for 139,276 delivered bytes.

Unit tests also cover screen state and query semantics. The optional --fcitx test runs Fcitx 5 with Pinyin on Xvfb and a private D-Bus session, checking ordinary key forwarding and Chinese text committed to the PTY. That run did not establish IBus or deliberately fragmented INCR coverage; current clipboard-transfer results are recorded in the 0.5.2 release report.

The graphics suite has passed all seven groups on Linux/Xvfb through a real PTY and window-pixel readback, recorded in the graphics result:

  1. Graphics capability and cell/window-size replies, with no image placed by a query.
  2. RGB, RGBA, and PNG colors, including four alpha levels and split PNG transmission.
  3. Chunked transmission, placement, soft deletion, image replacement, and data deletion.
  4. Source crop, clipping to the text viewport, and images below explicit cell backgrounds.
  5. Scrolling, window resize, primary/alternate isolation, and deletion without residual pixels.
  6. Malformed images, excessive dimensions, invalid base64, interrupted transfers, and subsequent keyboard/image recovery.
  7. Unmodified kitten icat 0.50 detecting stream, displaying a photo with explicit inline transport, and displaying a transparent-edge PNG through automatic detection.

The interrupted-transfer check observed 0 bytes of RSS growth between its before/after samples across 80 aborted uploads after earlier image tests warmed the process. This is an observation for that run, not a measurement of peak allocation or a general zero-growth guarantee. The test enforces a finite growth allowance and records the actual value in its JSON result.

The live Hyprland/XWayland run also passed on Hyprland 0.57.2: kitten icat --detect-support selected stream, and the real tools displayed both the photo and transparent-edge PNG. Only the owned test window was captured. The session's normal X0 pathname was absent; the probe used and removed its own temporary socket alias to the existing same-user XWayland endpoint, without changing compositor or authorization settings. This was the real desktop server, separate from Xvfb.

Native artifact verification also passed in workflow run 44165748395, on source 7535aa29f1a2728a78a446ffea6784dcbc2aae92:

Native environment Observed coverage Evidence
macOS Intel 8 session/protocol checks through a real AppKit application and Darwin PTY: geometry, cursor reply, image query, chunked RGBA, PNG, alternate screen, malformed-input recovery, deletion Native report
macOS Apple Silicon The same 8 session/protocol checks through a native application Native report
Windows x86_64 17 checks: native child/Unicode arguments, ConPTY query round trip, RGB/RGBA/PNG pixel readback, alpha, scrolling, clipping, resize, alternate screen, deletion, keyboard recovery Native report

Both historical macOS reports explicitly record pixel_readback: not_performed and ime_keyboard: not_performed; they do not establish either capability. Later native window-pixel acceptance is recorded in the six-platform candidate report and the 0.5.2 release report; those results do not turn the earlier runs into pixel tests. The Windows result uses the actual packaged ConPTY runtime and native window pixels, with the binary hash recorded in its report. This final native run includes the DA1 serialization fix described above. Formal packaging and native checks are defined in the release workflow.
