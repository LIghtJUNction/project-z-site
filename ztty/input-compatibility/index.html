Input protocol compatibility

The independent zinput codec remains no_std, uses alloc, forbids unsafe code and adds no dependencies. Unit tests verify generated bytes. The separate Linux X11 GUI gate below verifies delivery from X11 events through the frontend to an actual raw PTY, including terminal mode negotiation.

Changes and protocol evidence#

Case Previous behavior Implemented behavior Primary reference
Ctrl+Shift character shortcuts in legacy mode Shift collapsed into the Control mapping CSI-u preserves the Shift bit; Space retains its NUL exception Kitty legacy text keys, Ghostty keyboard encoder
Printable keypad keys in normal keypad mode with Kitty flags 1–7 Digits and operators became private-use key events when disambiguation was enabled Digits, decimal and operators remain UTF-8 text; report-all retains keypad identity and associated text; Num Lock overrides application-keypad mode; with Num Lock off, application-keypad mode keeps functional events Kitty disambiguation, report-all
Ctrl+tilde Literal tilde Control byte 30 Kitty legacy Control mapping
X10 tracking mode 9 No report Left, middle and right presses, with no modifier bits; no releases, motion or wheel events XTerm mouse tracking, Ghostty mouse encoder
Wheel buttons 4–7 and extra buttons 8–11 Only vertical Scroll events could be encoded Distinct button codes, horizontal wheel presses, extra-button releases and dragging XTerm other buttons and extended coordinates

Button numbers in MouseEvent are zero-based. Callers therefore pass 5 for X11 button 6 and 7 for X11 button 8. Buttons beyond X11 number 11 are rejected because their encoding overlaps modifier bits. Wheel releases and motion are suppressed. Tracking mode and coordinate encoding remain separate decisions: setting sgr_mouse does not turn tracking on.

The audit also checked existing Kitty alternate-key fields, base-layout fields, modifier transition state, event subfields, F3 disambiguation and associated-text release suppression. Those mechanisms already existed. New regression vectors exercise them without asserting that all native input paths are verified. Kitty protocol

Reproducible checks#

Run from the repository root:

sh
cargo test --locked -p zinput -j 1
cargo clippy --locked -p zinput --all-targets -j 1 -- -D warnings
cargo check --locked -p zinput --lib --target x86_64-unknown-none -j 1

The regression suite checks exact protocol vectors, all 32 Kitty flag combinations for Enter/Tab/Backspace release rules, all eleven xterm button numbers, invalid-button and coordinate overflow rejection, and append-only buffer reuse. Unknown or filtered mouse events must append no partial sequence. The bare-metal target check verifies that the library does not acquire a standard-library dependency.

Verified Linux X11 integration#

The API keeps its existing public struct and enum shapes. Frontends can pass extra button numbers through the existing MouseEvent::Press, Release and Motion variants. MouseEvent::Scroll remains a vertical-wheel convenience. The Linux frontend now routes all four wheel directions and buttons 8–11, retains held extra-button state for dragging, and propagates terminal tracking mode 9. Its release routing follows the owner of the original press when Shift changes; local selection and configured actions cannot leak unmatched releases to the PTY.

The real GUI regression in tests/input_gui.py passed all 27 vectors against the immutable candidate with SHA-256 b3d8fdb31d71ef9d1ed602b35673bf4648362fa354078e191e35a2cd75ac4631. The JSON evidence records exact expected and received bytes, binary/test/source hashes, the source commit and changes, pointer mapping, verified Xvfb socket ownership, and completed process cleanup. The actual window capture（历史附件） was visually checked: text is readable on the black background, overlays are closed, and no stray protocol bytes or drawing artifacts appear.

Group Vectors Verified behavior
Keyboard 3 Ctrl+I remains Tab; Ctrl+Shift+I produces distinct CSI-u; unshifted tilde plus Control produces byte 30
Wheels 4 Buttons 4–7 produce distinct vertical/horizontal SGR press codes without release reports
Extra buttons 8 Buttons 8–11 retain identity on SGR press/release and mode-1002 drag motion
Shift and press ownership 4 Primary/extra releases retain their remote destination after Shift changes; a local Shift press produces no remote release
Focus 1 Mode-1004 focus-out/in replies acknowledge both real transitions; subsequent motion/release cannot reuse old held-button state
X10 and mode changes 4 Left-button presses ignore modifiers; wheel/extra/motion probes are filtered; SGR selection is independent; resetting mode 9 preserves subsequently selected mode 1000
Configured actions 3 The custom search key and primary/extra mouse palette bindings consume their input and overlay text

The private Xvfb pointer exposes buttons 1–10. Tested buttons 1, 3 and 4–10 use XTEST, as do keyboard input and pointer movement. Button 11 uses explicitly labelled XSendEvent press/release events with XTEST pointer motion because this virtual device cannot generate button 11. This establishes X11 event routing for button 11; physical-device delivery remains a separate gate. The Control+tilde case uses an unshifted tilde mapping on an unused keycode in the private server, leaving the user's keyboard configuration untouched.

To reproduce, install Xvfb, Python Xlib and Pillow, build the Linux binary, then run from the repository root:

sh
python3 tests/input_gui.py \
  --binary target/release/ztty \
  --source-root "$PWD" \
  --output artifacts/input-gui.json \
  --screenshot artifacts/input-gui.png

The script uses an isolated runtime directory, broker socket and owned Xvfb. It compares real PTY bytes, waits for focus reports rather than a fixed delay, and fails if its owned processes remain after cleanup. The --source-root tree must contain tools/isolated_xvfb.py and match the supplied binary.

Remaining integration boundaries#

This gate covers the listed Linux X11 paths. Native Wayland, macOS and Windows event delivery, hardware buttons, IME/layout combinations, platform media keys, UTF-8 mouse coordinates, URXVT encoding and SGR pixel coordinates require their own acceptance tests. Complete Kitty/Ghostty equivalence is not established by these vectors. Ghostty separates mode-aware encoding from the frontend event source in its input guide.

Numeric keypad routing acceptance (2026-11-19)#

The keypad report records 177 X11/PTY input vectors, 14 font scenarios and 4 keypad overlay scenarios. The GUI gate requires setxkbmap in addition to Xvfb, Python Xlib and Pillow. It configures numpad:pc and kpdl:dot only on its private server to exercise the actual Num Lock/Shift layer and physical decimal/Delete key. The codec retains explicit Kitty identity and event negotiation when Num Lock overrides DECKPAM.

Clipboard images and application paste#

With the default bindings, Ctrl+Shift+V invokes ztty's text paste; Ctrl+V is delivered to the foreground application. In a locally running Codex CLI 0.170.0 composer, Ctrl+V requests an image attachment through Codex's own clipboard reader. Codex also recognizes a pasted path to an existing image file. These routes require the Codex process to have access to the corresponding clipboard or file; custom key bindings can change which application receives the shortcut. Codex image shortcut, clipboard reader, image-path handling.

The ztty 0.5.1 X11/XWayland frontend requests TARGETS before reading selection data. It accepts an advertised UTF8_STRING, text/plain;charset=utf-8, text/plain, or STRING target and requires the returned property type to match. UTF-8 text is validated after a complete transfer, including all INCR chunks; STRING retains its Latin-1 conversion. An image-only selection produces a visible no-text message without requesting image bytes or putting them into the PTY. OSC 52 reads use the same type checks. The native Wayland frontend already selects advertised text MIME types and now also validates the completed UTF-8 response.

The reported desktop advertised only image/png through a types-only Wayland query. Its X11 selection could not be inspected because the desktop denied X11 authorization; no real image contents were read. This establishes the available Wayland format, not the exact behavior of that desktop's XWayland conversion. The isolated Xvfb regression uses synthetic owners, including an image-only owner that incorrectly returns PNG bytes for text requests. Its scope is terminal text-paste negotiation and PTY delivery; it does not establish successful image attachment for every desktop or application. See the performance and reload report for the recorded results and their environment.
